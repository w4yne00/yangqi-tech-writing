# 初设、详设和总体架构设计

## 识别信号

初步设计、详细设计、总体架构、逻辑架构、技术架构、部署架构、接口设计、安全域、容灾、RTO/RPO。

## 写作目标

明确系统边界、组件关系、部署位置、数据流、接口、容量、可靠性和安全控制；设计选择应能追溯到需求、约束或风险，并区分现状、目标与演进。

## 默认策略

- 改写档位：`minimal` 或 `standard`。
- 默认 scope：`in-place`；新建草稿可用 `structural`。
- 无来源设计引用：`audit-only`。

## 强保护项

架构层级、系统及产品名称、网络区域、接口协议、型号、IP/端口、性能容量、RTO/RPO、标准编号和设计结论。见[保护项规则](../protected-spans.md)与[证据规则](../evidence-policy.md)。

## 应处理

- 删除“先进、领先、无缝、全栈赋能”等无指标修饰。
- 把产品宣传改为组件动作、关系、输入输出和边界。
- 降低“目标—能力—价值”连续同构段落。
- 将模糊权威改成明确设计依据或待确认项。

## 禁止动作

- 改变拓扑、组件关系、参数、接口或协议。
- 将“身份鉴别”等正式术语换成近义词。
- 将建议强化为必须，或将“应”弱化为“可”。

## 输出要求

保持章节、图号和引用关系；默认只附关键修订摘要和风险项。

### 正例

“管理区通过既有 API 网关调用统一身份服务；协议、端口和并发指标保持设计表 3-2 的既定口径。”

### 失败例

为“更自然”把“身份鉴别”改成“身份验证”，并把 RTO 2 小时改为“快速恢复”。
